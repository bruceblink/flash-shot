### R1：设置加载失败不应触发默认历史清理

位置：[启动入口](../crates/flash-shot-bin/src/main.rs#L44)、[设置加载](../crates/flash-shot-app/src/settings.rs#L84)、[历史加载](../crates/flash-shot-app/src/history.rs#L370)。

`UserSettings::load` 对未来版本设置返回 `Unsupported`，对无效 JSON 或读取失败也返回错误。
启动入口把所有错误都替换成默认设置，并继续使用原来的 `settings.json` 路径。
默认 `history_limit` 为 30，默认 `quick_save_directory` 为空。启动入口随后按该数量打开默认历史目录。
`ScreenshotHistory::load` 会立即执行超限清理。

触发条件是：默认历史目录已有超过 30 张截图，原设置允许保留 100/300 张，但本次设置加载失败。
仅启动应用就可能删除第 31 张及之后的历史截图。新版设置格式和损坏设置都能进入这条路径。
以后切换主题、语言或其他设置，还可能把默认结构保存回原文件，覆盖旧内容。
若原截图只在自定义目录，本条不表示默认回退会扫描并删除那个自定义目录。

现有 `newer_settings_are_not_silently_overwritten` 测试只检查 `load` 返回错误，没有覆盖启动回退、历史清理和后续保存。
后续应区分“文件不存在”与“文件存在但无法加载”。后者不得自动降低现有历史保留数量，也不得默认覆盖原设置。

### R2：历史加载的失败路径会先删除图片

位置：[加载顺序](../crates/flash-shot-app/src/history.rs#L399)、[超限清理](../crates/flash-shot-app/src/history.rs#L411)、[索引写入](../crates/flash-shot-app/src/history.rs#L435)。

`load` 先调用 `prune()`，再调用 `write_index()`。`prune()` 会直接删除旧图片。
当新索引不能写入时，`open_with_limit` 返回错误，但先前删除的图片无法恢复。
这与正常 `set_limit` 的“先提交索引，再删图片”顺序不同。

隔离复现使用两份合成文件和一份有效历史索引，上限先设为 2。
随后在索引临时文件位置创建同名目录，使索引保存失败，再按上限 1 重新打开历史：

```text
history_open_failed=true
older_image_survived=false
newer_image_survived=true
original_index_unchanged=true
```

同类情况也可能来自索引写权限不足，而图片删除仍被允许。启动回退不能恢复已经删除的文件。
现有 `retention_index_failure_keeps_the_previous_limit_and_files` 覆盖 `set_limit`，没有覆盖 `load`。
后续应统一加载与保留数量变更的提交顺序，并保留删除失败条目的重试入口。

### R3：可编辑项目可能只保存了一半

位置：[项目文件保存](../crates/flash-shot-app/src/app/workflow/file_io.rs#L376)、[标注文件保存](../crates/flash-shot-app/src/app/workflow/file_io.rs#L356)、[界面结果处理](../crates/flash-shot-app/src/app/workflow/exporting.rs#L395)。

可编辑项目由 PNG 和同名 `.annotations.json` 标注附属文件组成。
`save_editable_project` 先发布 PNG，再保存附属文件。第二步失败不会恢复已经替换的 PNG。

触发条件包括附属文件被占用、目标替换权限不足，或目标位置存在同名目录。
界面显示保存失败，但已有图片可能已被覆盖。重新打开项目时，新图片可能配上旧标注，或根本不能加载标注。
附属文件写入和替换失败后也没有统一清理 `.json.tmp` 的路径。

现有测试覆盖成功保存、重定位标注和重新打开，没有覆盖第二阶段失败。
后续应先准备完整的两份产物，再按明确的恢复步骤发布。失败时保留旧项目，或明确撤回本次新建文件。
不需要因此更换项目格式或引入通用存储框架。

### R4：滚动拼接会忽略稀疏页面的新内容

位置：[重叠候选选择](../crates/flash-shot-app/src/scroll.rs#L215)、[追加像素](../crates/flash-shot-app/src/scroll.rs#L269)、[平均差计算](../crates/flash-shot-app/src/scroll.rs#L337)。

检测器从最大重叠开始，接受第一个平均字节差不超过 6 的候选。
大面积白底会稀释少量正文像素的差异。因此，“平均差小”不等于“这段内容确实重叠”。

隔离复现直接调用真实 `stitch_vertical`：两张 `1×100` BGRA 帧分别代表页面第 0～99 行和第 20～119 行。
页面为白底，第 50 行与第 110 行为黑色。实际滚动 20 像素，正确输出应为 `1×120`，并保留两行黑色内容。

```text
detected_overlaps=[100]
stitched_dimensions=1x100
expected_dimensions=1x120
dark_rows_in_output=[50]
```

实现返回成功，却丢掉新增的第 110 行内容及尾部 20 行。该构造是对白底稀疏内容的最小化测试，不是原生滚动验收。
现有高对比度模式测试没有覆盖这种输入。
后续应增加有区分力的重叠检查；不能确定时拒绝追加并允许重试，而不是静默丢内容。

### R5：子进程输出管道未及时读取

位置：[OCR 执行](../crates/flash-shot-app/src/ocr.rs#L113)、[FFmpeg 探测](../crates/flash-shot-app/src/recording.rs#L1428)。

两处实现都把 stdout/stderr 设为管道，先轮询子进程是否退出，退出后才执行 `wait_with_output()`。
当任一路输出超过管道容量时，子进程等待父进程读取，父进程却在等待子进程退出，最终触发超时。

OCR 隔离复现使用测试子进程替代 Tesseract，只调用真实 `check_support`，不创建或识别图片：

| 测试输出 | 结果 | 耗时 |
| --- | --- | --- |
| 32 字节版本输出 | 成功 | 29 ms |
| 1 MiB 版本输出 | `TimedOut` | 20,006 ms |

长截图 OCR、详细错误输出和设备列表都可能超过小型管道容量。FFmpeg 探测具有相同等待顺序和 10 秒超时，但本轮没有运行其大输出复现。
真实录屏进程已经用独立读取线程持续读取输出，不应把这一问题误报为所有 FFmpeg 流程都受影响。
后续应在等待期间持续读取两路输出，限制保留大小，并在超时或读取失败后回收进程与读取线程。

### R6：退出应用没有等待录屏收尾

位置：[退出回调](../crates/flash-shot-app/src/app.rs#L712)、[关闭工作流](../crates/flash-shot-app/src/app/workflow/capture.rs#L877)、[录屏控制对象析构](../crates/flash-shot-app/src/recording.rs#L393)。

退出回调执行同步 `shutdown` 后返回空 future。`shutdown` 丢弃 `recording_control`，而它的析构函数只设置停止请求。
录屏工作线程没有可供退出回调等待的完成句柄。
正常的 MP4 收尾、临时文件发布和失败清理仍在该工作线程中执行。

用户在录屏期间从托盘退出时，应用可以先于工作线程退出。
Windows Job Object 能终止残留 FFmpeg 进程，但不能代替容器收尾或删除 `.part-…mp4`。
因此该次录屏可能未成为最终文件，临时文件也可能残留。
本轮确认的是缺少等待边界；未通过真实录屏退出测量残留概率。

后续应明确退出策略，并用有界等待完成正常停止或强制终止后的清理。
验收必须覆盖录制、暂停、启动中和停止中退出，不能只验证 `RecordingProcess` 析构会结束进程。

### R7：终止事件不能与可丢弃进度采用同一处理方式

位置：[事件队列](../crates/flash-shot-app/src/recording.rs#L477)、[完成事件](../crates/flash-shot-app/src/recording.rs#L533)、[失败事件](../crates/flash-shot-app/src/recording.rs#L685)、[接收循环](../crates/flash-shot-app/src/app/workflow/recording.rs#L923)。

事件队列容量为 32。进度、暂停、恢复、完成和失败事件都调用 `try_send`。
队列满时，终止事件也会被丢弃。发送端退出后，界面接收循环直接结束，没有清除仍存在的 `recording_control`。

该问题依赖接收任务长时间不能消费事件；本轮没有证明真实桌面上出现过这种拥塞。
但队列满后的事件丢失和状态未恢复可以从实现直接确认。
一旦触发，进程可能已经停止，界面却仍保留录制或停止状态，后续操作返回工作线程已结束的错误。

后续先加入确定性的队列饱和测试，再以最小改动保证终止状态可观察，并核验通道异常关闭后的恢复。
进度允许合并或丢弃，不应为此引入无界队列或重做整套事件系统。

## 3. 工程验证缺口

这些项目影响验证可信度，不等同于已经发生的产品故障：

1. [CI](../.github/workflows/ci.yml#L45) 的 check、Clippy 和 test 没有 `--all-features`，未覆盖可选的 `dev-tools`。
2. [Release](../.github/workflows/release.yml#L25) 固定 Rust `1.95`，本地与质量 CI 使用 stable；源码检查同样没有覆盖全特性。根目录没有 `rust-toolchain.toml`。
3. [Windows 捕获测试](../crates/flash-shot-infra-windows/src/capture.rs#L459) 默认会读取真实桌面；[快捷键测试](../crates/flash-shot-infra-windows/src/shortcut.rs#L391) 默认会注册系统热键。全工作区测试不是无副作用的纯单元测试集合。

后续在 Q1 中统一 stable/MSVC 基线、锁文件和全特性静态检查，明确普通测试与真实桌面验收的执行入口。
当前 Windows 主线不因此自动增加 Linux/macOS 发布承诺，也不需要本轮监测 GitHub CI。
