### R8：覆盖确认必须针对最终写入路径

位置：[普通导出](../crates/flash-shot-app/src/app/workflow/exporting.rs#L83)、[标注导出](../crates/flash-shot-app/src/app/workflow/exporting.rs#L319)、[项目导出](../crates/flash-shot-app/src/app/workflow/exporting.rs#L392)、[普通格式处理](../crates/flash-shot-app/src/app/workflow/file_io.rs#L310)、[PNG 后缀处理](../crates/flash-shot-app/src/app/workflow/file_io.rs#L330)、[标注后缀处理](../crates/flash-shot-app/src/app/workflow/file_io.rs#L341)。

三个流程都先等待 `prompt_for_new_path` 返回，再分别调用 `export_path`、`annotation_document_path` 或 `png_path`。
这些函数可能改写用户在对话框中选择的路径，随后直接调用支持替换已有文件的写入函数，没有针对最终路径的确认步骤。

明确触发方式：目标目录已有 `capture.png`，用户输入不存在的 `capture` 或 `capture.txt`。
对话框处理的是原路径；应用随后把它改成 `capture.png` 并调用最终替换。原 PNG 可能在没有针对该文件确认的情况下被覆盖。
项目保存与独立标注保存具有同类路径变化。项目由 PNG 与 `.annotations.json` 构成；B3 的双文件备份与恢复不能代替最终路径的覆盖授权。

本轮核对了锁定版本 `gpui-pre-windows 0.3.6` 的 Windows 实现：`file_save_dialog` 只配置建议名称与 `All files (*.*)`，返回对话框结果，不替调用方执行上述扩展名规则。
这是依赖源码和应用调用链的结论，本轮没有运行真实 Save 对话框，不声称已观察到用户数据被覆盖。

现有路径测试只验证补后缀和保留支持格式，没有覆盖“归一化后的文件已存在，用户拒绝覆盖”。
应在最终路径确定后执行覆盖决策。拒绝时保留原文件，保持编辑会话可重试。
本项不要求更改第三方库、项目格式或重构全部对话框；仅标注文件已存在时的独立覆盖规则不在本轮自动变更范围。

### R9：快速保存清理失败会让旧图脱离历史管理

位置：[记录截图与清理](../crates/flash-shot-app/src/history.rs#L333)、[快速保存完成入口](../crates/flash-shot-app/src/app/workflow/exporting.rs#L742)。

`record_with_source` 先把超出上限的旧图从条目中截去，写入截断索引并更新内存，再逐个删除旧图。
历史已满、下一次 Quick Save 触发清理时，如果某张旧图被外部查看器以不允许删除的方式打开，删除会报错，但该图已不在内存和落盘索引中。
图片没有被删除，却从 Library 消失。后续加载只读取索引，不扫描目录，因此解除占用、重启应用也不会自动恢复该条目或重试清理。

本条不表示新截图丢失，也不否定 B2 对 `load` 的修复；缺陷发生在正常保存的 `record_with_source` 路径。
`set_limit` 直接入口也有同类顺序，但当前设置窗口采用分阶段清理，不把该入口误写成设置页实际流程。
现有测试覆盖记录时索引写入失败、加载时删除失败，没有覆盖记录时删除失败后的索引可重试性。
应先提交包含候选项的完整索引，再仅移除确认已删除的条目，分别报告新图保存与历史清理结果。

### R4：稀疏正文仍可能在拼接成功后丢失

位置：[重叠选择](../crates/flash-shot-app/src/scroll.rs#L215)、[追加像素](../crates/flash-shot-app/src/scroll.rs#L269)、[平均差计算](../crates/flash-shot-app/src/scroll.rs#L337)。

检测器从最大重叠开始，接受第一个平均字节差不超过阈值的候选。白底会稀释少量正文差异，因此整帧也可能被误认为重叠。
旧报告用两张 `1×100` 合成帧复现：实际滚动 20 行，页面第 50、110 行有黑色内容。
正确结果应为 `1×120`，实现返回 `1×100`，缺少新增内容。该算法相对旧审查基线未变。

本轮现有 `scroll::tests` 11 项通过，但没有该稀疏正文回归，因此不能据此关闭 R4。
修复需核验高度和正文像素；无法确认重叠时返回可重试错误，不静默接受。原生白底页面交互仍须另行验收。

### R5：探测进程会被未读取的输出管道阻塞

位置：[OCR](../crates/flash-shot-app/src/ocr.rs#L117)、[FFmpeg 探测](../crates/flash-shot-app/src/recording.rs#L1428)。

两处均设置 stdout/stderr 管道，先轮询进程退出，再调用 `wait_with_output()`。
输出填满任一路管道后，子进程等待读取，父进程等待退出，正常输出也会在 OCR 20 秒或 FFmpeg 10 秒期限后报超时。
旧 OCR 隔离探针的 32 字节输出成功，1 MiB 输出在约 20 秒超时；本轮未重新执行该探针，也未执行 FFmpeg 大输出复现。

现有测试没有 stdout、stderr、双管道填满的覆盖。应在等待期间持续读取，限制保留字节数，并在超时、取消或读取失败后回收进程与读取线程。
OCR 与探测入口分别修改和验证，不提前建立通用进程框架。
真实录屏已有独立读取线程，不能把本条扩大为全部录屏输出读取均有问题。

### R6：退出请求不等于录屏收尾完成

位置：[退出回调](../crates/flash-shot-app/src/app.rs#L712)、[工作流关闭](../crates/flash-shot-app/src/app/workflow/capture.rs#L877)、[控制对象析构](../crates/flash-shot-app/src/recording.rs#L393)。

退出回调执行同步 `shutdown` 后返回空异步任务；清除 `recording_control` 只请求停止，不等待工作线程。
该线程仍负责停止 FFmpeg、完成 MP4、发布最终文件或清理暂存文件。用户在录制、暂停、启动中或停止中退出时，应用可能先于这些步骤结束。
Job Object 可以结束残留进程，不能代替文件收尾或 `.part-…mp4` 清理。

本轮确认缺少完成等待边界，没有测量真实退出时产物损坏或残留的发生概率。
后续先明确退出时保留或放弃产物的策略，再实现有期限的等待与清理；使用测试进程验证协调，再做实际录屏退出验收。

### R7：终止事件仍采用可丢弃的发送方式

位置：[32 项事件队列](../crates/flash-shot-app/src/recording.rs#L477)、[完成发送](../crates/flash-shot-app/src/recording.rs#L533)、[失败发送](../crates/flash-shot-app/src/recording.rs#L685)、[接收循环](../crates/flash-shot-app/src/app/workflow/recording.rs#L923)。

完成和失败事件都用 `try_send` 且忽略失败。队列已满时，工作线程可以完成文件处置后丢弃终止事件。
发送端关闭后接收循环直接结束，而 `recording_control`、停止状态与托盘复位只在终止事件处理分支清除。
若达到拥塞前提，界面可能一直显示录制或停止，无法开始新会话。

现有启动失败、异常退出测试的事件队列未预先填满，不覆盖该条件。
本轮未证明真实 UI 出现过足够长的消费停顿。保留条件性 P2，先测试满队列成功、失败和接收端关闭，再决定最小修改。
进度可丢弃或合并，终止状态必须可观察；不增加无界通道，不扩大为录屏事件系统重写。
