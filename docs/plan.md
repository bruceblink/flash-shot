# 下一阶段开发计划

更新日期：2026-08-16
规划范围：`v0.1.2` 稳定版收口与 `v0.2.0` 质量阶段

## 1. 当前基线

Flash Shot 的功能主线已经完成。Windows 单显示器、100% 缩放环境中的截图、标注、复制、
保存、Pin、历史、滚动截图、OCR 和录屏闭环已有 Release 原生验收；CI、便携包、安装器、
校验清单与 GitHub draft Release 流程也已建立。

下一阶段不再以增加截图工具或在线服务数量为目标，而是把现有能力变成可持续维护、可重复发布、
可在更多真实 Windows 环境中证明可靠的产品。

截至本计划更新时：

- `main` 版本为 `0.1.1`，最新 CI 已通过；
- GitHub 上的 `v0.1.1` 仍是 draft，并且标签早于当前主线的生产剪贴板稳定性修复；
- 单显示器 100% 主流程已通过，150%/200% 缩放仍缺少真实硬件证据；
- 负坐标双屏与混合 DPI 双屏仍按既有决定暂缓，不纳入当前承诺；
- 配置真实 HTTPS 端点后的翻译成功、失败与重试闭环尚未执行，但它不是核心截图发布阻塞项；
- 4K 标注的真实交互帧时间尚未形成可重复的目标硬件基线；
- `crates/flash-shot-app/src/app/overlay.rs` 与原生验收 runner 已经很大，继续堆叠场景会显著提高回归和维护成本。
- 设置页和覆盖层仍以英文硬编码文案为主，缺少应用级国际化资源；现有 `translation.rs` 只是 OCR 文本的
  外部翻译服务边界，不能替代 UI 本地化。
- 当前 UI 将少量高频动作、低频诊断动作和重复的全屏快捷操作放在同一层，需要重新整理信息架构，
  保持核心动作短路径并为后续语言和功能扩展留出稳定组件边界。

详细环境状态与证据以 [Windows 手工验收记录](windows-manual-acceptance.md) 为准。本计划只保留
下一阶段的目标、顺序和退出标准，不再复制逐次运行日志。

## 2. 开发原则

1. **先稳定后扩展**：在 `v0.2.0` 前不增加新的截图、标注、OCR、翻译或录屏能力。
2. **发布基于当前主线**：不得直接发布早于生产修复的旧 draft 资产；标签、源码、runner 和验收报告
   必须指向同一提交。
3. **一个风险一个切片**：行为修复、结构重构、依赖升级和文档变更分别提交，验证通过后立即推送。
4. **真实证据与静态门禁并存**：原生窗口、全局输入、系统剪贴板、FFmpeg 和 DPI 行为不能只靠单元测试
   宣称通过。
5. **失败必须可恢复**：超时、前台抢占、剪贴板争用、磁盘错误和外部进程异常都必须安全停止，保留
   可诊断结果，并清理输入、窗口、临时文件与子进程。
6. **控制文档寿命**：需求、当前计划、操作流程和验收矩阵各保留一个事实来源；已完成的过程计划留在
   Git 历史，不继续在 `docs` 中累积。

## 3. 优先级

| 优先级 | 含义 | 当前主题 |
| --- | --- | --- |
| P0 | 阻塞可信发布或可能破坏用户数据/主流程 | 当前主线补丁发布、复制/保存/录屏清理、发布资产一致性 |
| P1 | 不阻塞补丁发布，但影响长期稳定与开发效率 | 故障注入、长时间资源门禁、大文件拆分、4K 交互基线、UI 重构与国际化 |
| P2 | 依赖额外硬件、服务或明确产品决策 | 150%/200% 矩阵、双屏混合 DPI、真实翻译端点、Linux/macOS |

P0 未关闭前不开始新功能。P1 重构不得与行为变化混在同一提交。P2 只在前置环境可用或范围被明确恢复
后执行。

## 4. 阶段 A：发布当前主线补丁版

目标：把 `v0.1.1` 标签之后已经验证的修复收敛为新的补丁版本，避免发布不包含最新剪贴板修复的旧
draft。

### A1. 冻结与版本边界

- 审计 `v0.1.1..main` 的提交范围，确认只包含应进入补丁版的修复、测试、CI 与文档变更；
- 将 Cargo 版本提升到 `0.1.2`，同步锁文件、安装器、脚本示例和用户文档中的版本事实；
- 用标签提交范围生成双语 changelog，不手工复制 GitHub 默认说明；
- 不移动或覆盖既有 `v0.1.1` 标签。

### A2. 当前源码发布门禁

必须在同一候选提交上完成：

```powershell
cargo fmt --all -- --check
cargo check --workspace --all-targets
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

然后执行与本次补丁直接相关的 Release 验收：

- 工具栏 Copy 与 Enter Copy 各 1 次预热和 30 次有效系统剪贴板样本；
- 三 Pin 共存、生产剪贴板复制、Capture/Cancel、逐个关闭与 60 秒生命周期 soak；
- 普通截图的 Save、Pin、Copy 和 teardown 清理闭环；
- 显示器、区域、窗口录制的开始、暂停、恢复、停止、MP4/FFprobe 与子进程清理；
- 便携包启动和安装、启动、卸载生命周期；
- release manifest、SHA-256 sidecar、资产清单和版本一致性。

系统剪贴板与全局输入场景只在可丢弃桌面显式授权运行。报告、截图、runner 哈希和构建提交必须能相互
对应。

### A3. 发布退出标准

- 新标签从通过全部门禁的提交创建；
- GitHub hosted runner 成功生成新的 draft 资产；
- 下载后的安装器、便携包、sidecar 和 manifest 全部复核通过；
- 人工完成核心截图、标注、复制、保存、Pin 与录屏冒烟后再发布；
- 旧 `v0.1.1` draft 不再被描述为当前候选版本。

## 5. 阶段 B：可靠性与故障恢复

目标：从“功能能用”进入“故障发生时仍可预测”。每一项都是独立的小功能或测试切片。

### B1. 主流程故障注入

- 剪贴板被短暂占用、消费者超时和 owner HWND 创建失败时，验证有界重试、错误反馈与零残留；
- 快速保存目录只读、临时文件同步失败、目标名冲突和历史索引写入失败时，验证原子性与回退路径；
- FFmpeg 缺失、启动失败、运行中退出和停止超时时，验证状态恢复、MP4 处理和 Job Object 清理；
- 历史目录包含损坏 PNG、文件消失或切换目录时，验证有界队列继续处理且不会写回陈旧结果。

退出标准：每个故障都由确定性测试或隔离探针复现；失败后应用可立即重新截图或录屏，且没有孤儿进程、
窗口、按键、半成品文件或永久 busy 状态。

### B2. 长时间资源稳定性

- 先记录 Capture/Copy/Pin/Close、历史浏览和录屏停止的 Release 长时基线，再根据实测波动设门槛；
- 报告句柄、线程、工作集、私有提交、窗口注册表、后台任务和子进程的起点、峰值与结束值；
- 将短时波动与持续增长分开，禁止凭单次样本定义通用内存阈值。

退出标准：重复操作后资源回到稳定区间，Capture preflight 可用，报告可由 CI 外的受控 Windows 会话
重复执行。

### B3. 性能基线

- 保持启动、快捷键到覆盖层、Copy 外部消费者和连续捕获现有门槛；
- 建立 4K 非空标注的真实交互帧时间基线，区分 GPUI 预览与 CPU 导出；
- 为长图 PNG 编码记录尺寸、吞吐、峰值内存和像素指纹，不把文件对话框等待混入编码指标。

退出标准：每项指标有清楚的计时边界、预热、样本数、p50、p95、最大值和失败数；回归门禁来自稳定
基线而不是任意百分比。

## 6. 阶段 C：可维护性改造

目标：降低原生交互代码和验收工具继续演进的成本，不改变用户行为。

### C1. 拆分原生验收 runner

- 将 `overlay-interaction-acceptance` 按 Capture、Copy、Pin、Scroll、Recording 和共享 Windows 输入设施
  拆分模块；
- 保持现有 CLI 参数、默认安全策略、报告 schema 与输出目录兼容；
- 抽取前台所有权、按键释放、watchdog、截图和 cleanup 断言，避免场景各自实现不同规则。

每次只迁移一个场景，迁移前后用同一场景的单元测试与 Release 报告比较；禁止一次性重写整个 runner。

### C2. 收敛应用模块边界

- 按渲染、输入、选择变换、菜单/工具状态和导出生命周期逐步缩小 `crates/flash-shot-app/src/app/overlay.rs`；
- 继续把文件 I/O、识别、录屏和平台调用留在现有 workflow/platform 边界；
- 为非平凡状态更新和 Windows 生命周期函数补充面向初学者的函数级注释；
- 模块边界已通过多个切片验证后，采用小型 workspace；领域、应用、Windows 基础设施、GPUI 界面、验收库
  和唯一二进制的职责与迁移顺序见 [Workspace crate 迁移设计](workspace-crate-design.md)。第一阶段已完成
  `flash-shot-domain`、`flash-shot-app` 与 `crates/flash-shot-bin` 中唯一 `flash-shot` 包的工作区落地，
  第二阶段已完成 `flash-shot-image` 的图像核心提取，Windows 基础设施阶段已完成显示器枚举、屏幕捕获、
  全局快捷键和托盘首个切片；后续阶段继续按该文档拆分。

### C3. 依赖与供应链维护

- 以独立提交审计 Rust 依赖公告、许可证和未使用依赖；
- GPUI/Zed 升级单独立项，必须通过编译、真实覆盖层、设置、Pin、性能和打包矩阵；
- 不在功能修复中顺带升级锁定的 GPUI 提交或 FFmpeg 契约。

退出标准：行为和报告契约不变，全量门禁通过，大文件的职责边界与测试归属更清楚。

## 6.5 阶段 C+：UI 信息架构、视觉系统与国际化

目标：在不改变截图、标注、录屏和历史数据契约的前提下，重做用户界面层级、视觉语言和文案资源，
让核心操作更短、更容易理解，也让后续能力可以按模块扩展。

### C+1. 信息架构与动作收敛

- 将 `Capture` 作为唯一的高频主入口，保留区域、全屏和焦点窗口三种核心捕获动作；
- 从设置页移除重复的“全屏 Copy/Save/Pin”快捷按钮，统一在覆盖层、托盘或明确的 `More` 菜单中提供；
- 将低频诊断、目录检查、更新检查和兼容性操作放到对应设置分组的次级区域，不与主动作并排竞争；
- 保持核心流程最多两层可达，按钮名称描述结果而不是内部实现；
- 为每个保留动作定义稳定的语义 ID，避免通过显示文案判断行为。

退出标准：Capture、Library、Record、App 四个入口的职责不重叠；真实键鼠操作可以从设置或覆盖层完成
截图、标注、Copy、Save、Pin、录屏和清理，不需要寻找重复按钮。

### C+2. 应用级国际化基础

- 新增独立于 OCR/外部翻译服务的 UI `Locale` 与稳定 `TextKey` 资源目录；
- 首批支持 English 与简体中文，保留英文作为缺失资源的安全回退；
- 将语言选择写入版本化用户设置，启动时加载，切换后立即刷新所有可见 GPUI surface；
- 禁止在用户可见 UI 中继续拼接英文状态句；动态数量、路径、快捷键和错误详情使用带参数的本地化模板；
- 资源键、按钮 ID、自动化报告字段和快捷键契约保持语言无关。

### C+3. 现代化视觉系统

- 建立统一的语义颜色、间距、字号、圆角、边框、禁用态、焦点态和状态反馈 token；
- 统一按钮层级：每个区域最多一个主要动作，次要动作使用低对比度按钮，破坏性动作单独强调；
- 在覆盖层、Pin、设置和历史中统一工具栏高度、控件命中区、键盘焦点和错误反馈，不用装饰性面板堆叠层级；
- 优先使用图标加 tooltip 表示缩放、复制、保存、关闭等熟悉动作，长文本只保留在不易误解的命令上；
- 以 420x420、520x640、980x760 三种窗口尺寸同时校验中英文、深浅主题和窄选区布局。

### C+4. 分组迁移与验收

按以下顺序迁移，每组单独提交和验收：

1. 设置窗口导航、页标题、主按钮和系统状态；
2. Capture 覆盖层、More 菜单、Copy/Save/Pin/Cancel 反馈；
3. Library、历史筛选、批量删除和空状态；
4. Record、OCR、翻译、更新和错误/忙状态；
5. Pin 工具栏、快捷键提示和窗口生命周期反馈。

退出标准：选择简体中文后，核心 UI 不再出现可见英文硬编码（品牌名、路径、快捷键和外部错误详情除外）；
所有保留功能在中英文下均可由真实鼠标和键盘完成，截图、报告、资源清理和快捷键行为保持不变。

## 7. 阶段 D：真实环境矩阵

该阶段依赖真实硬件，不能用逻辑缩放、合成截图或单元测试代替。

### D1. 单显示器高 DPI

在 150% 和 200% 缩放下分别验证：

- 智能窗口/控件候选、自由拖选、移动、普通/Shift/Alt 缩放和键盘微调；
- Copy、Save、Pin、滚动截图和录屏的物理像素尺寸；
- 设置窗口、窄选区、More 菜单、标注上下文和状态反馈的布局；
- 多 Pin 移动、缩放、透明度、复制、保存、Capture 共存和清理。

退出标准：报告中的实际 DPI/scale 与目标一致，导出逐像素正确，关键截图无截断、重叠或不可达控件。

### D2. 暂缓项

- 负坐标双屏和混合 DPI 双屏继续暂缓；恢复范围后按
  [Windows 手工验收记录](windows-manual-acceptance.md)作为独立阶段执行；
- 真实翻译端点只在有可丢弃 HTTPS 测试服务时验收，不把它升级为核心发布阻塞项；
- Linux 和 macOS 只保留可行性研究，不承诺功能对等或发布资产。

## 8. 阶段 E：`v0.2.0` 候选版

进入候选版前必须满足：

- 阶段 A 已发布，P0 故障恢复项全部关闭；
- 至少完成一轮可重复长时资源基线和 4K 交互性能基线；
- 验收 runner 与 overlay 至少完成一个可验证的模块化切片，未引入报告契约回归；
- UI 信息架构、语言资源和核心工作流迁移至少完成一轮，中英文双主题截图与真实键鼠验收通过；
- 可用硬件范围内的 DPI 矩阵已执行，未执行项保持显式暂缓；
- README、需求、架构、计划、验收矩阵和分发文档之间没有冲突或失效链接；
- CI、Release workflow、下载复核和人工 UI 冒烟全部通过。

`v0.2.0` 仍以 Windows-first、原生 Rust/GPUI 和本地处理为产品边界。代码签名可以在具备可信证书与
运营预算后单独推进；在此之前继续清楚说明未签名资产风险，不把签名伪装成已完成。

## 9. 暂不安排

- 新的标注工具、识别引擎、翻译供应商或录屏后端；
- 协作、云同步、插件 API、浏览器版或移动版；
- 为追求形式上的功能对等而启动 Linux/macOS 全量移植；
- 未经真实 Windows 验收的 GPUI 主线跟随升级；
- 与当前稳定性、维护性或发布目标无关的大规模 UI 重设计。

## 10. 推荐执行顺序

1. 完成文档事实源清理并保持链接有效；
2. 以当前 `main` 为基础收口并发布 `v0.1.2`；
3. 依次完成一个故障注入切片、一个长时资源切片和一个 4K 性能切片；
4. 每次迁移一个验收场景，逐步拆分大型 runner；
5. 在真实硬件可用时执行 150%/200% 矩阵；
6. 汇总通过证据，进入 `v0.2.0` 候选版。

每完成一项都先运行风险匹配的验证，再以单一 Conventional Commit 提交并立即推送；未通过或只完成一部分
的项目保留在本计划中，不标记为完成。
